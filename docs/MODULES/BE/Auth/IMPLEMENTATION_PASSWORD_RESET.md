# 이메일 비밀번호 재설정

2026-11-26 사용자 요청으로 AUTH-05를 구현한다. 기존 로그인 상태의 비밀번호 변경과 별도로,
이메일 소유권을 일회용 링크로 검증해 비밀번호를 재설정한다.

## HTTP와 화면 계약

| 경로 | 동작 |
| --- | --- |
| `POST /auth/forgot-password` | 이메일을 받고 대상 계정에만 링크 발송. 자격·회원 여부와 무관한 동일 200 응답 |
| `POST /auth/reset-password` | 토큰과 `new_password`를 받아 재설정. 성공 시 `message`와 `login_url` 반환. 무효·만료·사용된 링크는 동일 400, 정책·유출 비밀번호는 422 |
| `/auth/forgot-password` | 로그인 화면에서 진입, 이메일 입력과 비열거 발송 안내 |
| `/auth/reset-password` | fragment 토큰을 메모리로 옮기고 주소에서 제거, 새 비밀번호와 확인 입력 후 명시적으로 제출 |

링크는 PRD의 1시간 유효기간을 유지한다. 각 API에 IP당 분당 5회 제한을 따로 적용하고,
같은 계정에는 60초 이내 재발송하지 않는다. 재발송 성공 시 이전 링크를 무효화한다.
대상은 활성·이메일 인증 완료·비밀번호 보유 계정이며 owner도 포함한다. 소셜 전용 계정의
비밀번호 연결은 범위 밖이다. GET이나 메일 스캐너 방문만으로 토큰을 소비하지 않는다.

2026-11-27 사용자 요청으로 미등록 주소에는 가입 안내, 활성·인증 완료 Google 전용 계정에는
Google 로그인 안내를 보낸다. Google 안내는 비밀번호가 없고 실제 `oauth_accounts`에 Google
연결이 있는 계정만 대상으로 하며 비밀번호를 설정하거나 복구 토큰을 발급하지 않는다.
미인증·탈퇴·기타 소셜 계정에는 안내나 토큰을 보내지 않는다. 삭제 계정의 이메일
점유도 확인해 가입 가능한 미등록 주소로 안내하지 않는다. 안내 메일은 주소 HMAC별 60초
무응답형 제한을 기존 limits MemoryStorage로 적용한다. 프로세스 재시작 때 초기화되고
멀티워커에서는 워커 수만큼 느슨해질 수 있다. 유효한 비밀번호 계정의 링크 발급 제한은
기존 DB 잠금과 60초 간격을 유지한다.

## 저장과 동시성

`password_resets`에는 토큰 HMAC과 발급 당시 비밀번호의 목적별 HMAC 태그를 저장한다.
태그는 기존 비밀번호 변경 뒤 발급 전 링크가 작동하지 않게 한다. 원문 토큰과 비밀번호
해시는 응답·로그에 넣지 않는다. 메일 링크는 설정의 `APP_BASE_URL`을 사용한다.

HIBP 조회와 새 비밀번호 해싱은 User 잠금 전에 수행하며, 변경 직전 User를 먼저 잠근 뒤
최신 토큰과 계정 자격을 다시 확인한다. 비밀번호 갱신, 기존 refresh 삭제, 신뢰 기기 폐기와
재설정 토큰 소비를 함께 commit한다. 실패하면 rollback하고 같은 토큰의 동시 제출은
하나만 성공한다. 정상 로그인·비밀번호 변경과 같은 User 우선 잠금 순서를 따른다.

2026-11-27 현재 비밀번호와 같은 값의 재설정을 거부하도록 보완했다. 유효한 토큰과
최신 계정 자격을 확인한 뒤 잠근 현재 해시로 기존 비밀번호 검증 함수를 호출한다.
bcrypt의 새 salt 때문에 해시 문자열끼리 비교해서는 같은 비밀번호를 판별할 수 없다.
검증 후 만료 시각을 다시 확인하고, 토큰이 여전히 유효하면서 같은 비밀번호라면
`422 새 비밀번호는 현재 비밀번호와 달라야 합니다`와 no-store를 반환한다.
rollback하며 현재 해시·refresh·신뢰 기기·TOTP·재설정 토큰을 변경하지 않고 완료 메일도
보내지 않는다. 프런트는 기존 422 처리로 문구를 표시하고 링크를 유지하므로 다른 새
비밀번호를 입력해 재시도할 수 있다. 무효·만료·사용된 링크에서는 동일 여부를 검사하지 않는다.

자동 로그인과 인증 쿠키 쓰기는 하지 않는다. 완료 뒤 다시 로그인하도록 안내한다.
2026-11-27 사용자 요청으로 owner 제외를 제거했다. TOTP 시크릿·등록 확인 시각·마지막
성공 step을 수정하지 않고 기존 refresh와 신뢰 기기를 폐기한다. 비밀번호에 결합된 변경 전
관리자 pending은 새 해시와 맞지 않아 거부된다. 기존 일반 로그인과 계정 화면의 owner
봉쇄는 유지하며, 새 비밀번호만으로 일반 독자 세션이나 관리자 세션을 발급하지 않는다.
활성 TOTP 계정은 새 비밀번호로 관리자 로그인한 뒤 기존 인증기의 코드를 다시 입력한다.
TOTP 미등록 owner는 기존 관리자 첫 등록 게이트를 유지한다. TOTP 분실 복구는 이번 범위에
포함하지 않는다.

성공 응답의 `login_url`과 완료 메일 변수는 모든 계정에서 `{APP_BASE_URL}/auth/login`이다.
2026-11-27 사용자 수정 요청으로 owner를 관리자 화면으로 안내했던 분기를 제거했다.
독자 사이트에서 시작한 재설정은 독자 완료 화면에 남고, 로그인 버튼도 `/auth/login`으로
고정한다. 이전 서버 응답에 관리자 URL이 들어 있어도 화면의 목적지로 사용하지 않는다.
자동 이동·로그인은 하지 않고 역할이나 목적지를 요청 입력으로 받지 않는다. 반환할 이메일과
URL은 commit 전에 확보해 완료 뒤 별도 조회 실패가 재설정 결과를 가리지 않게 한다.
기존 stateless access는 잔여 수명 동안 유효할 수 있다. 새 로그인과 늦은 재설정 응답이
쿠키를 덮어쓰지 않으며, 다른 기기의 이전 refresh로는 갱신할 수 없다.

발송과 완료 알림은 commit 뒤 기존 Resend BackgroundTasks로 전송한다. 발송 장애 시
기존 메일 서비스처럼 DB 변경을 되돌리지 않는다. 2026-11-27 사용자 요청으로 직접 HTML
발송에서 Resend 게시 템플릿으로 전환했다. 발신자·제목·본문은 Resend에서 관리하고 API는
alias와 변수만 보낸다. 만료된 재설정 행은 기존 토큰 정리 작업에서 제거한다.

### 사용자 Resend 템플릿 연결

| Alias | 용도 | 문자열 변수 |
| --- | --- | --- |
| `password-reset` | 비밀번호 재설정 링크 | `reseturl` |
| `password-reset-complete` | 재설정 완료 안내 | `loginurl` |
| `gmail-registered` | Google 전용 계정 안내 | `loginurl` |
| `non-registered` | 미등록 주소 가입 안내 | `registerurl` |
| `already-registered` | 가입 중복 안내 | `loginurl` |

사용자가 Resend에서 작성·게시한 템플릿을 그대로 참조한다. 서버는 alias와 변수만
전달하며 본문·버튼·제목·발신자를 생성하거나 덮어쓰지 않는다. 로컬 HTML 템플릿은
관리하지 않는다. `reseturl`에는 서버가 프런트 주소와 일회용 fragment 토큰을 조합해 넣는다.
[Resend 발송 API](https://resend.com/docs/api-reference/emails/send-email)의 published alias와
변수 계약을 따른다.

`loginurl`은 owner를 포함해 `{APP_BASE_URL}/auth/login`이며,
`registerurl`은 `{APP_BASE_URL}/auth/signup`이다.
문의는 사용자가 작성한 템플릿의 mailto 링크를 유지하며 Reply-To를 추가하지 않는다.
2026-11-27 사용자 등록 후 읽기 조회에서 위 다섯 템플릿과 `email-verification`의 published
상태, 변수 이름, From·Subject 설정을 확인했다. 실제 메일은 도구로 발송하지 않았다.
2026-11-27 사용자 승인에 따라 두 alias의 `-1` 접미사만 제거했다. 템플릿 내용과
`loginurl`·`registerurl` 변수 계약은 변경하지 않았다.

2026-11-27 로컬 조사에서 API 키 설정 유무를 확인했고, 해당 키의 Resend 템플릿·도메인
읽기 요청은 200이었다. 설정 발신 도메인은 verified였으며 사용자 템플릿 추가 전에는 기존 가입 인증과
중복 가입 안내뿐이었다. 최초 조사 시 로컬 재설정 토큰 행은 0개였으므로 키·발신 도메인 오류로
단정하지 않고 요청 계정의 자격 제외 여부를 먼저 확인한다. 비열거 응답은 발송 여부를
보장하지 않는다. 조사에 이메일 주소·토큰·키 원문을 출력하거나 실제 메일을 발송하지 않았다.

화면은 no-store·noindex·no-referrer를 적용한다. 토큰은 fragment에서만 읽고 즉시 주소에서
지우며 비밀번호 확인 값은 API로 보내지 않는다. 이탈 시 비밀번호와 토큰을 폐기하고,
BFCache 복원과 늦은 응답이 비밀값이나 이전 화면 상태를 복구하지 않도록 한다.
메일 링크로 직접 여는 재설정 페이지에서는 React가 fragment를 지우기 전에 주소를 수집하지
않도록 클라이언트 Sentry 초기화를 생략한다. 로그인·재요청 링크는 전체 페이지 탐색을 사용한다.

### 같은 페이지의 새 링크와 늦은 응답

2026-11-27 리뷰에서 같은 탭의 fragment 변경을 읽지 않는 문제와, 요청 중 이메일을 바꾸면
이전 주소의 응답이 현재 주소의 성공으로 표시되는 문제를 확인해 보완했다.

재설정은 최초 마운트와 `hashchange`에서 토큰을 읽고, 즉시
`history.state`를 보존해 fragment를 제거한다. 새 토큰 수신 시 비밀번호·오류·완료 상태와
이전 요청 세대를 폐기한다. 새 토큰은 명시 제출할 때만 사용하며 이전 요청의 늦은 성공이나
실패는 새 폼과 토큰을 변경할 수 없다. 입력이 없거나 이미 완료·폐기된 화면에서도 새 링크를
받으면 다시 사용할 수 있다. BFCache 복원만으로 이전 토큰을 복구하지 않는다.

메일 요청은 발송 중 이메일 입력과 제출을 잠근다. 주소 변경과 재요청 시작 시 기존
안내를 지우고, 응답은 제출한 정규화 주소와 요청 세대에 결합한다. 자동완성이나 프로그램
입력 등으로 주소가 바뀌어도 이전 응답으로 새 주소의 발송을 확인하지 않는다.
이탈·unmount·BFCache는 이전 요청을 무효화하며, 오래된 요청의 완료가 새로운 요청의
대기 상태를 풀거나 남겨 놓지 않도록 한다.

실제 사용자 계정 비밀번호 변경이나 메일 발송은 도구로 수행하지 않았다.

# 가입 전 이메일 인증과 도메인 분리 로그인 표시

2026-11-23 사용자 요청. 기존 가입 후 인증 흐름을 Resend 이메일 인증번호 확인 후 계정 생성으로 바꾼다. 비밀번호 확인은 [이슈 #68](https://github.com/Sy3058/d-web/issues/68)을 함께 해결한다.

## 가입 계약

| 요청 | 역할 |
| --- | --- |
| `POST /auth/signup/send-verification` | 이메일만 받아 6자리 인증번호 발송, challenge ID 반환 |
| `POST /auth/signup/verify-email` | challenge ID와 6자리 코드 확인, 인증된 이메일 반환 및 HttpOnly 가입 증명 쿠키 발급 |
| `GET /auth/signup/verification` | 가입 증명 쿠키를 확인해 유효한 경우에만 이메일 반환 |
| `POST /auth/signup` | 이메일·닉네임·비밀번호와 쿠키의 증명을 검증해 계정 생성 |

사용자는 이메일만 입력해 Resend 인증번호 메일을 받는다. 가입 화면에서 6자리 번호를
입력하고 확인하면 서버가 증명 쿠키를 발급하고 “이메일이 인증되었습니다”를 표시한다.
메일 앱이나 다른 기기에서는 번호만 확인하고 원래 가입 화면에서 계속 진행한다.

이미 계정이 있는 이메일의 인증 요청에는 인증번호 대신 중복 가입 안내 메일을 보낸다.
기존 미인증·탈퇴 계정도 이메일 UNIQUE를 점유하므로 같은 안내를 보낸다. 응답의 형식과
상태, 이메일별 재발송 제한은 신규 주소와 동일하다. 중복 주소의 challenge는 만료 상태로
저장해 인증번호 확인이나 가입 증명 발급에 사용할 수 없다. 기존 계정 정보는 변경하지 않는다.

번호는 암호학적 난수로 생성하며 10분 뒤 만료한다. 이메일별 60초 재발송 제한과 challenge별
최대 5회 검증을 DB 행 잠금으로 적용한다. 오답 횟수는 오류 응답 전 commit한다. 재발송은
challenge ID와 코드를 교체하고 이전 증명·코드와 횟수를 초기화한다. 코드는 challenge ID와
결합한 HMAC 해시만 저장하고 원문은 메일에만 넣는다. 코드와 증명은 로그에 남기지 않는다.
인증 성공 뒤 challenge를 재사용할 수 없으며, 가입 증명은 15분 HttpOnly·host-only 쿠키다.

인증 완료는 서버 응답으로만 결정하며 다른 이메일의 증명으로 가입 필드를 열지 않는다.
새로고침 시에는 HttpOnly 증명 쿠키로만 인증 상태를 복구한다. 이메일 주소나 challenge ID만으로
인증 완료를 조회하거나 최종 가입할 수 없다. 이메일 변경과 오래된 응답은 세대 가드로 분리한다.

프런트는 인증 완료 후 닉네임·비밀번호·비밀번호 확인을 받는다. 확인용 비밀번호는 최종
요청에서 제외한다. 독자 가입·로그인·비밀번호 변경은 공통 눈 아이콘으로 비밀번호를
표시하거나 숨길 수 있으며 버튼이 폼을 제출하지 않는다.

최종 가입은 서버가 증명의 이메일·만료·미사용 여부를 확인한다. HIBP 확인과 해싱 중에는
DB 잠금을 유지하지 않고, 생성 직전에 잠근 최신 증명으로 다시 검사한다. 계정 생성과
증명 소비는 같은 트랜잭션이다. OAuth 등의 동시 계정 생성은 SAVEPOINT로 충돌을 처리해
기존 계정을 덮어쓰지 않고 동일 완료 응답으로 수렴한다. 가입 직후 자동 로그인하지 않는다.

## 기존 계정과 배포

기존 `email_verifications` 링크와 재발송은 이미 생성된 미인증 계정을 위해 유지한다.
기존 링크는 query token과 확인 버튼을 사용한다. 신규 가입용 fragment 링크 화면은 제거한다.
미인증 계정은 비밀번호가 맞아도 로그인·refresh·보호 API 접근이 거부된다. 기존 access도
거부하며 데이터를 일괄 인증 처리하지 않는다. 로그인 실패 화면에서 인증메일 재발송으로
진입할 수 있다. 공개 콘텐츠의 비회원 열람과 webhook·결제 재확인 처리는 유지한다.

이미 적용한 초기 migration을 유지하고 코드용 challenge·시도 횟수를 후속 migration으로 추가한다. 배포 시 기존 Compose의 migrate
성공 뒤 API를 시작한다. 전송은 기존 Resend API 키를 사용한다.
실제 발신 도메인 검증과 수신은 배포 환경에서 사용자가 확인한다.

신규 인증번호 메일은 사용자가 Resend에 게시한 alias `email-verification`을 사용한다.
REST 요청의 `template.id`에 alias를 넣고 `template.variables.verifycode`에 6자리 문자열을
전달한다. `verifycode`는 템플릿에서도 String 타입으로 정의해 앞자리 0을 보존한다.
인증번호 발송에는 별도 `html`·`text`·`react`와 `from`·`subject`를 보내지 않는다.
발신자와 제목은 게시된 템플릿의 From·Subject를 사용한다. 유효시간 안내는 서버의
10분 정책에 맞춘다. 중복 가입 안내도 alias `already-registered`와 문자열 변수 `loginurl`로
발송하며 템플릿의 From·Subject를 사용한다. 기존 계정의 인증 링크 재발송은 HTML 메일과
`EMAIL_FROM`을 계속 사용하므로 환경변수는 유지한다. 템플릿의 From도 Resend에서 검증된
도메인이어야 한다.
[Resend 발송 API](https://resend.com/docs/api-reference/emails/send-email)의 템플릿 계약을 따른다.

## 인증 기록 정리

가입 인증 기록은 기존 만료 토큰 정리 작업에서 기동 직후와 24시간마다 정리한다.
`expires_at`이 지났고, `proof_expires_at`이 없거나 만료됐으며, `last_sent_at`부터
재발송 제한 60초가 지난 행만 삭제한다. 코드가 만료됐어도 유효한 가입 증명은 보존한다.
즉시 만료 상태로 저장한 중복 주소 challenge도 재발송 제한이 끝나기 전에는 삭제하지 않는다.

## 로그인 표시

API host-only 쿠키는 인증 요청에 전달되지만 다른 프런트 호스트의 `document.cookie`에는
나타나지 않는다. 기존 메뉴는 힌트가 없으면 `/auth/me` 자체를 건너뛰었다. 메뉴와 개인
진행도는 힌트 없이도 서버에 세션을 확인하고 refresh를 복구한다. 최종 401만 비회원으로
판정하며 일시 장애를 로그아웃이나 비회원 진행도로 단정하지 않는다. 힌트는 가능한 환경의
초기 표시 최적화로만 남기고 쿠키 Domain을 넓히거나 공유 SSR에 개인 데이터를 넣지 않는다.

## 검증 범위

- 인증번호 메일·앞자리 0, 만료·오답 횟수 소진·재사용·재발송·동시 확인.
- 인증 전 User 미생성, 이메일 결합, 최종 가입의 일회성·동시성, 기존 계정 불변.
- 미인증 로그인·기존 access·refresh 거부와 기존 링크 인증 호환.
- 같은 화면의 인증 상태 전환과 새로고침 복구, 다른 이메일 증명 거부, 비밀번호 재입력과 눈 아이콘.
- 힌트 없는 유효 로그인, 최종 401, 일시 장애, 늦은 응답과 뷰어 개인 진행도.

자동 검증은 정적 검사·단위·통합 테스트다. 브라우저 실기능과 실제 메일 수신은 사용자가 확인한다.

코드 전환 검증: Backend 전체 ruff·pytest 1,263개, Frontend lint·Astro check·388개 테스트·build,
Admin 타입 재생성·lint·139개 테스트·build, 최종 빌드 SSR 20개가 통과했다. 대소문자 혼합 이메일의
최종 가입과 단계별 Enter 제출도 회귀 테스트로 확인했다. 임시 DB에서 초기 revision에
기존 사용자와 인증 증명을 넣은 뒤 `b4c9d0e1f2a3` 적용·drift 없음·되돌림·재적용과 데이터 보존을
검증하고 임시 DB를 제거했다. 로컬 개발 DB도 이 revision까지 적용했다. VPS 배포와 실제
Resend 수신·브라우저 스모크는 아직 수행하지 않았다.

Resend 게시 템플릿 연동 후에도 Backend 전체 포맷·Ruff·1,265개 테스트가 통과했다.
발송 HTTP 요청에서 alias·변수 이름·문자열 코드와 HTML 필드 부재, 기존 HTML 메일 호환,
API 키 미설정·HTTP 오류·민감 정보 비로깅을 확인했다. 실제 메일은 테스트에서 발송하지 않았다.

템플릿 From 사용 변경 후에도 Backend 포맷·Ruff·전체 1,265개 테스트가 통과했다.
환경변수 발신자가 있어도 인증번호 요청에는 `from`이 없고, HTML 메일에는 기존 발신자가
포함되는 것을 확인했다. 실제 메일 수신은 사용자가 확인한다.

중복 주소의 최초 인증 요청도 안내 메일만 발송하도록 변경했다. 인증·미인증·탈퇴 계정의
계정 불변, 동일 응답 형식, 재발송 제한과 중복 challenge 만료를 회귀 테스트로 확인한다.
인증번호와 중복 안내 템플릿은 From·Subject를 모두 Resend에서 관리하며 발송 요청에서
생략한다. `_send`는 제목 생략을 허용하고 HTML 인증 링크 메일은 기존 제목·발신자를 유지한다.
변경 후 Backend 포맷·Ruff·전체 1,268개 테스트가 통과했다. 실제 메일은 자동 테스트에서 발송하지 않았다.

만료 가입 인증 기록 정리 추가 후 스케줄러 테스트 18개와 Backend 전체 1,270개 테스트,
포맷·Ruff 검사가 통과했다. 만료·사용 완료 행 삭제, 유효 코드·증명·재발송 제한 보존과
정리 후 재발급·반복 정리의 멱등성을 확인했다.

# TROUBLESHOOTING - 전체 pytest에서 매번 다른 테스트 1개가 간헐 401 (시계 역점프)

대상: backend (JWT 검증 전부 - access / oauth_tx / admin pending), 로컬 WSL2 개발 환경
관련 구현: `src/lib/auth.py` `JWT_LEEWAY_SECONDS`, `../Episodes/IMPLEMENTATION_EPISODE_SOFT_DELETE.md` §4(발견 경위)
발생: 2026-07-26~27, #85 작업 중 발견. **M1부터 잠복하던 환경 문제로 #85 diff와 무관**

## 증상

- 전체 pytest ~17회 중 3회 실패. 매번 **다른** 테스트 1개가 401(기대 201/204), 직후 테스트부터는 전부 정상.
- 같은 클라이언트·같은 쿠키로 **직전 요청은 성공**했는데 바로 다음 요청이 401. 스위트 48초, 토큰 TTL 15분이라 만료 아님.
- 실패가 실행 시간이 긴 파일(`test_admin_episodes.py`, 스위트 시간의 ~40%)에 편중. 단독·파일 단위 실행으론 재현 안 됨.

## 왜 어려웠나

실패 순간의 증거(401 응답 본문, DB 상태)를 한 번도 수집하지 못한 채 가설만 3번 세웠다 헛발질했다. 코드 경로를 아무리 읽어도 안 나오는 게 당연했다 - 원인이 코드에 없었기 때문이다.

구조 추론으로 좁힌 것도 있다: 테스트는 앱과 같은 세션을 공유하고 `expire_on_commit=False`라, 직전 요청이 성공(커밋)한 직후엔 `session.get(User)`이 identity map에서 바로 유저를 돌려준다. 즉 "user 행 소실" 계열 가설은 **구조적으로 불가능** - 남는 건 쿠키/토큰 계열이었다.

## 계측 (가설 → 예측 → 실측)

가설마다 "맞다면 계측에 무엇이 찍혀야 하는지"를 먼저 적고, 실측이 예측과 일치할 때만 살렸다.

1. `get_current_user`의 401 분기 4곳에 임시 진단 print(사유·쿠키 이름 대조·decode 예외·같은 세션 vs 새 커넥션의 users count).
2. Postgres `log_statement='mod'` + `log_line_prefix`에 db명 - "users를 지운 게 누구인가"의 최종 증거용.
3. 전체 스위트 반복 루프(최대 15회, `-x`) - 첫 실패에서 pytest 출력·PG 로그·`pg_stat_activity` 스냅샷 **자동 수집**. 루프 중 backend 파일·명령 동결(변인 통제).

## 결정적 증거

11번째 run에서 재현(TOTP stage2 401). 증거 사슬:

1. **PG 순차 로그의 연속 두 줄이 `15:10:56.461` → `15:10:54.636`** - 시계가 ~1.9초 뒤로 점프한 직접 관측. WSL2/NTP 보정은 시계를 계단식으로 되돌릴 수 있다(운영 서버의 chrony slew와 다름).
2. 진단 print 무발화 + stage2의 DB 쓰기 전무 - "쿠키·유저 조회 문제 아님, 토큰 검증 자체에서 거부"와 정합.
3. 결정적 재현: `iat`를 2초 미래로 박은 토큰을 프로젝트 `decode_token`이 ImmatureSignatureError로 거부(PyJWT 2.13), `leeway=10`이면 같은 토큰 통과.

메커니즘: 점프 **전**에 발급된 토큰의 `iat`가 점프 **후** 시점엔 "미래"가 된다. PyJWT(2.6+)는 기본 leeway=0으로 미래 iat를 거부한다. 발급·검증이 같은 프로세스여도 일어난다. "딱 1개 실패 후 전부 정상"(다음 테스트는 점프 후 시각으로 새 토큰 발급)과 파일 편중(오래 도는 파일일수록 점프에 맞을 확률 큼)이 전부 설명된다.

## 해결

`src/lib/auth.py`에 `JWT_LEEWAY_SECONDS = 10`을 상수로 두고 `jwt.decode` 3곳(access / oauth_tx / admin pending) 전부에 적용. 실측 점프(1.9초)의 5배 여유. exp 판정도 같이 10초 관대해지지만 최단 수명 토큰(600초) 대비 1.7%라 수용.

회귀 테스트 2건: iat 5초 미래 토큰을 `decode_token`이 수용(단위) + TOTP stage2가 iat 미래 pending 쿠키로 200(통합, 실측 실패의 결정적 재현). 변이 실험(leeway=0)으로 정확히 그 2건만 빨강 확인. 수정 후 전체 스위트 15연속 그린(수정 전 실패율 ~18%/run).

## 잔여 리스크 (수용)

- 10초를 넘는 대형 역점프(호스트 절전 복귀 등)는 여전히 실패 가능. 스위트 실행 중 발생은 드물고, 운영 서버(Hetzner, chrony slew 보정)는 해당 없음.
- TOTP step 차원의 역점프 영향은 `_accept_totp` docstring에 기왕 문서화된 수용 사항.

## 교훈

- **"매번 다른 테스트 1개만 실패 + 직후 전부 정상 + 오래 도는 파일에 편중"은 임의 시점 일회성 환경 이벤트(시계·디스크·네트워크)의 서명이다.** 코드 경로를 읽어서는 절대 안 나온다.
- 가설이 2~3번 연속 빗나가면 추론을 멈추고 **실패 순간을 자동 포획하는 계측**으로 전환할 것. 이번 건의 비용 대부분은 계측 전환이 늦은 데서 나왔다.
- 같은 머신이라도 시계는 단조가 아니다 - `jwt.decode`엔 leeway가 필수. (MISTAKES "JWT / PyJWT" 절에 요약 기록)

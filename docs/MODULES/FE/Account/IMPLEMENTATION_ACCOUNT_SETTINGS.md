# 계정과 프로필 편집

2026-11-16. 사용자 요청에 따라 마이페이지 명칭을 계정으로 바꾸고, 요약과 편집을 각각의 페이지로 분리한다. 단일 프로젝트 폴더의 fe/feat/account-settings에서 작업하며 BE 통합 저장은 099e0d2에 별도 커밋했다.

## 화면

- `/my`: 설명 문구 없이 계정 제목, 프로필 구분선 아래 원형 이미지·닉네임과 프로필 수정 버튼을 둔다. 계정 보안에는 이메일을 읽기 전용으로 표시하고 로컬 비밀번호 계정에만 비밀번호 변경 버튼을 제공한다. 이메일 관리·패스키·2FA 설정은 추가하지 않는다.
- `/my/profile`: 원형 이미지 미리보기·파일 선택/제거·닉네임 입력과 하단 변경 내용 저장 버튼을 제공한다. 계정 정보 편집은 전용 페이지에서 하고 이미지 자르기만 모달로 진행한다. 돌아가기/취소는 계정으로 전체 이동한다.
- `/my/password`: 현재/새 비밀번호/확인 입력과 취소·변경을 제공한다. 소셜 전용 계정은 외부 로그인 서비스 관리 안내를 표시한다.
- 메뉴와 결제 복귀의 `/my` 링크 표시도 계정으로 통일한다. 구매내역·설정 경로는 그대로다.

## 한 번 저장과 입력 수명

프로필 편집값은 React 메모리에만 둔다. 작가 썸네일과 같은 react-easy-crop 6.2.2를 FE에도 연결해 이미지를 선택하면 자르기 모달에서 위치·1~3배 확대와 원형 선택 미리보기를 제공한다. 적용하면 편집 페이지의 미리보기에 반영하고, X·취소·바깥 클릭·Escape는 해당 자르기 초안을 폐기한다. 처리 중에는 중복 적용과 닫기를 막는다. 닫힌 뒤 파일 선택 입력으로 포커스를 복원한다. 선택 영역 적용은 canvas에서 256×256 PNG 초안으로 변환할 뿐 업로드하지 않는다. 자르기 중에는 최종 저장을 막고 적용/취소를 먼저 선택하게 한다. 원본 로드 실패·범위 초과·캔버스 실패는 오류로 표시하고, 소스 교체/화면 종료 뒤 늦은 결과는 무시한다. 원본은 업로드하지 않으며 잘라낸 PNG를 서버가 다시 제한 검증·WebP 변환한다. 이미지 선택·제거·닉네임 입력만으로 API를 호출하지 않는다. 저장할 때 PUT /auth/me/profile에 multipart nickname과 필요한 file/remove_image를 함께 보낸다. Content-Type/boundary는 브라우저가 정한다. 닉네임과 이미지의 DB 변경은 BE 단일 commit 계약을 따른다.

선택 이미지는 JPEG/PNG/WebP·5MB를 먼저 보조 검증하고 실제 파일 검증·중앙 256px WebP 변환·R2 저장은 서버가 담당한다. 원본 자르기 소스와 결과 미리보기의 Object URL은 교체·취소·저장 성공·최종401·unmount 때 각각 해제한다. 페이지를 저장 없이 벗어나면 입력을 폐기한다. 일반 재진입은 서버 조회값으로 시작하고, BFCache 복원은 마지막 서버 응답으로 확정한 프로필을 기준으로 초안을 초기화한다. 브라우저 저장소에 편집값·비밀번호를 보관하지 않는다.

저장 중에는 ref 잠금과 disabled로 중복 제출을 막고 unmount 이후 응답은 반영하지 않는다. 성공하면 공통 NoticeDialog에 “프로필 정보를 수정했어요.”를 표시한다. 바깥 클릭·X·확인·Escape로 닫으며 닫은 뒤 닉네임 입력으로 포커스를 복원한다. 서버가 확정한 프로필로 편집 기준을 갱신하고 `dweb:account-updated` 이벤트로 닉네임 힌트를 즉시 메뉴에 반영한다. 실패 시 오류와 입력을 유지한다. 네트워크 오류는 미반영으로 단정하지 않고 서버 상태 재확인을 안내한다.

비밀번호는 가입 정책을 재사용하고 Zod 객체 refine에서 확인 필드에 오류를 연결한다. 2026-11-20 사용자 요청으로 성공 시 입력만 비우고 현재 기기의 새 세션을 유지한다. 재로그인 링크나 편집 잠금을 표시하지 않고 성공 안내를 띄우며, 설명은 “다른 기기에서는 로그아웃됩니다.”로 제공한다. 가입 조건의 중간 점은 쉼표로 바꿨다. 실제 최종401은 기존처럼 재로그인을 요구한다. 기존 access의 최대15분+10초 잔여 유효성 계약은 유지한다. 두 편집 폼은 method=post를 명시해 hydration 전 기본 GET 제출로 입력이 URL에 포함되는 것을 막는다.

관리자(owner)는 계정 요약에서 비밀번호 변경 버튼을 표시하지 않고 편집 경로 직접 진입·복구에서도 입력을 제공하지 않는다. 로컬 비밀번호가 없는 소셜 전용 계정도 기존처럼 변경할 수 없다. 서버도 잠근 최신 역할로 owner를 거부한다. 후속 검증은 Frontend lint·Astro check·376 tests·build·SSR16을 통과했고, 성공 뒤 BFCache 복구와 재편집 및 관리자 진입 차단 회귀를 포함한다. 실제 브라우저 조작은 수행하지 않았다.

## 개인 정보 경계

세 페이지 모두 getMe(cookie) 기반 인증 SSR과 no-store/noindex를 유지한다. 로그인 redirect에도 두 헤더를 명시한다. 최종401은 로그인 이동, 조회 장애는 보호된 오류 화면으로 구분한다. 개인 계정은 비공개 SSR과 편집 섬 초기 데이터에만 포함하고 공유 메뉴 SSR/공개 캐시에는 넣지 않는다. 미래 댓글의 공개 프로필과 이메일·has_password를 담은 본인 DTO는 구분한다.

## BFCache 미저장 입력 복원 수정 (2026-11-17)

코드 리뷰에서 unmount 정리만으로는 BFCache 복원 시 초안이 남는 문제를 확인했다. no-store가 BFCache 보존까지 항상 막는 것은 아니므로 ProfileEditor와 PasswordEditor는 pagehide와 persisted=true인 pageshow에서 초안을 정리한다. 일반 최초 pageshow는 입력을 건드리지 않는다.

프로필은 마지막 저장 응답의 닉네임·이미지로 돌아가며 선택 파일·제거 표시·자르기 원본·미리보기·오류·성공 알림을 폐기하고 두 Object URL을 즉시 해제한다. 비밀번호는 명시한 빈 defaultValues로 세 입력을 초기화해 같은 값을 다시 입력·제출해도 정상 처리한다. 기존 로그인 요구 상태는 보존한다.

이탈·복원·unmount 때 요청 세대를 무효화해 이전 성공·실패·finally가 복원된 화면이나 새 요청의 busy/잠금을 변경하지 못한다. BFCache 복원에서는 편집을 잠근 뒤 이탈 전에 진행 중이던 저장의 완료를 기다리고 getMe로 최신 본인 계정을 확인한다. 확인된 프로필을 새 기준으로 반영한 뒤에만 다시 저장할 수 있다. 인증 종료는 재로그인, 조회 실패는 새로 열어 확인하도록 잠금과 오류 안내를 유지한다. 이를 통해 직전 저장이 성공했는데 오래된 닉네임을 후속 이미지 저장에 다시 보내는 일을 막는다. 늦은 자르기 결과도 현재 원본 URL과 화면 수명을 대조해 무시한다. 이미 서버로 발송된 저장 요청의 취소나 DB rollback을 보장하는 기능은 아니다.

실제 컴포넌트의 페이지 전환 이벤트·이미지 수명·재입력·이전 저장/복원 조회 경쟁·서버 기준 재확인·StrictMode·리스너 정리 회귀48개를 포함해 전체352 tests·lint/check/build·SSR16을 통과했다. 읽기 전용 재검토에서도 두 P2가 해결됐고 추가 차단 문제는 발견되지 않았다. 실제 브라우저 BFCache 조작은 실행하지 않았다. [Chrome no-store/BFCache 정책](https://developer.chrome.com/docs/web-platform/bfcache-ccns?hl=en).

## 개발 서버 복구 기록

## 뷰어 개발 의존성 캐시 격리 보완

2026-11-16 사용자의 구매 회차 진입에서 TipTap 세 모듈과 개발 툴바가504 Outdated Optimize Dep로 실패했다. 구매 권한 조회가 아니라 뷰어 hydration 모듈 로딩 실패였다. 실행 중 dev가 변환한 Viewer.tsx의 hash와 디스크 캐시 hash가 달랐고, 디스크의 캐시 변경 시각은 astro check 실행과 일치했다. 설치된 Astro check→sync→임시 Vite 서버 경로도 확인했다.

astro.config.mjs의 로컬 integration에서 astro:config:setup command에 따라 Vite cacheDir을 node_modules/.vite/dev·sync·build 등으로 분리했다. 원고/권한/결제 코드는 바꾸지 않았다. 개발 서버 정상 재시작과 캐시 최적화 뒤 Viewer·extensions·React·TipTap 세 파일·개발 툴바를 실제 URL로 조회해200을 확인했다. 실행 중 dev에 check와 build를 적용해도 같은 TipTap URL이200으로 유지되고 sync/build가 별도 metadata를 쓰는 것을 확인했다. 기존 탭은 이전 경로를 캐시했으므로 강력 새로고침이 필요하다.

## 세션 복구와 메뉴 동기화 (2026-11-19)

계정 요약·프로필·비밀번호·설정 SSR은 getMeOnServer로 access만 조회한다. 페이지 요청에 refresh 전용 쿠키가 없으므로 서버에서 자동 갱신하지 않는다. 인증된 SSR의 개인 내용과 no-store/noindex는 유지하고, 401에는 개인정보 없는 AccountSessionRecovery를 렌더한다. 브라우저의 기존 getMe와 공용 wrapper로 갱신한 뒤 해당 페이지 내용을 표시한다. 최종 401은 로그인 안내, 서버·네트워크 장애는 재시도로 구분한다. 로그인 페이지로 잘못 이동하거나 새로고침을 반복하지 않는다. 계정 요약은 AccountOverview를 SSR과 복구 화면이 공유한다.

AccountMenu는 힌트로 첫 표시를 유지한 뒤 진입·포커스·BFCache 복원·계정 갱신에서 서버 닉네임을 대조한다. 뷰어 컨트롤 표시 때는 힌트가 달라진 경우에만 추가 확인해 반복 호버의 불필요한 조회를 피한다. 확인된 이름은 같은 힌트의 재검증 장애로 과거 값으로 되돌리지 않으며 늦은 요청은 세대 검사로 무시한다. 로그아웃 중에는 메뉴 확인을 시작하지 않고 완료 후 잠금을 풀어 BFCache 복원을 허용한다. 갱신·로그아웃의 응답 순서는 메뉴만이 아니라 공용 API wrapper에서 조율한다.

Frontend lint·Astro check(오류0, 기존 hint1)·373 tests·build, Admin lint·139 tests·build, production SSR16개 검사를 통과했다. 서버 확인은 refresh 호출 없이 401을 복구 셸로 넘기는지 검사하고, 브라우저 회귀는 실제 공용 wrapper로 갱신 성공·최종401·503/네트워크·재시도를 검증한다. 공유 회귀는 로그인·로그아웃·비밀번호 변경과 늦은 갱신 응답의 순서·동일 본문 재시도·Web Locks를 검사한다. 실행 중 개발 사이트에서도 표시 힌트만 가진 /my가200 복구 셸이고 새 모듈과 API가200인 것을 확인했다. 실제 브라우저의 쿠키·뒤로 가기 조작은 자동으로 수행하지 않았다.

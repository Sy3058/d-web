# 코드 리뷰 원칙

영역별 체크리스트(`CODE_REVIEW_BE.md` / `CODE_REVIEW_FE.md` / `CODE_REVIEW_ADMIN.md`)와 함께 사용한다.
체크리스트가 *무엇을 검사하는가*라면, 이 문서는 *어떻게 리뷰하고 응답하는가*를 정한다.

기반: [Google Engineering Practices - Code Review](https://google.github.io/eng-practices/review/) 를 1인 프로젝트 맥락에 맞게 각색.

---

## 0. 이 프로젝트의 맥락

- 저자 = 나
- 리뷰어 = Opus 4.7 (`/model opus` 호출, `@docs/reviews/...` 첨부)
- 따라서 Google 원칙 중 *팀 협업 절차*(응답 SLA, 멘토링, 에스컬레이션)는 *self-discipline 강화*로 재해석한다.

---

## 1. 리뷰의 기준 (Standard)

**완벽이 아니라 "코드 헬스를 개선하는가"가 기준.**

- 머지 전 상태보다 명확히 개선되었다면 승인. "더 좋게 만들 여지가 있다"는 이유만으로 머지를 막지 않는다.
- 추가 개선은 후속 PR/이슈로 분리.
- 단, **🚨 Critical은 예외** - 보안·데이터 무결성 위반은 항상 머지 금지.

---

## 2. "Cleanup later" 금지

이 프로젝트에서 가장 위험한 함정.

- "다음 PR에서 정리할게요"는 **거의 일어나지 않는다** (1인 프로젝트는 특히).
- TODO를 남길 거면 **GitHub 이슈로 등록**하고 코드에 이슈 번호를 적는다.
  - ⭕ `# see #42 - Signed URL 만료 시간 조정 필요`
  - ❌ `# TODO: 나중에`
- 예외: 진짜 긴급 핫픽스. 그래도 cleanup 이슈는 *같이* 등록.

---

## 3. Small PR 원칙

(`guides/GUIDE_COMMIT.md`의 "한 커밋 하나의 변경"을 PR 단위로 확장)

- 한 PR = 하나의 자기완결적 변경
- 100줄 적정, 1000줄 too large (단, 파일 수와 함께 봐야 함)
- 리팩토링은 기능 변경과 분리된 PR
- 큰 작업은 **stacking PR** - 선행 PR 머지 후 다음 시작

---

## 4. 리뷰어가 확인할 일반 관점

영역별 체크리스트는 *이 프로젝트 특유의 violation*에 집중한다.
그 외 다음은 항상 검토:

| 항목 | 질문 |
|------|------|
| Design | 변경이 이 모듈에 속하는가? 추상화 위치가 맞는가? |
| Functionality | 의도대로 동작하는가? 엣지 케이스·동시성은? |
| Complexity | 빠르게 이해되는가? 미래에 필요할 법한 일반화는 없는가? |
| Tests | 변경에 맞는 테스트가 있는가? 테스트가 실제로 실패할 수 있는가? |
| Naming | 의미를 충분히 전달하고 과도하게 길지 않은가? |
| Comments | "왜"를 설명하는가? "무엇"을 설명한다면 코드를 단순화하라. |
| Consistency | 기존 코드 컨벤션을 따르는가? |
| Documentation | 빌드·환경·API 변경 시 관련 문서도 업데이트했는가? |
| Context | 이 변경이 시스템 전체 헬스를 올리는가, 복잡도만 늘리는가? |

## 5. 리뷰 코멘트 작성 규약

### 5.1 심각도 prefix

영역별 CODE_REVIEW의 4단계와 정렬:

| Prefix | 의미 | 머지 영향 |
|--------|------|-----------|
| `🚨 Critical` | 보안/데이터 무결성 위반 | **머지 금지** |
| `⚠️ Major` | 버그 가능성, 유지보수 악화 | 수정 필요 |
| `💡 Nit:` | 스타일·미세 개선 | 머지 가능 (선택 수정) |
| `📌 FYI:` | 참고 정보, 미래 고려 | 머지 가능 |

### 5.2 톤

- 코드를 비판하라, 사람을 비판하지 마라.
  - ❌ "왜 여기 스레드를 썼나요?"
  - ⭕ "이 동시성 모델은 성능 이득 없이 복잡도만 늘립니다. 싱글스레드가 명확합니다."
- **이유를 함께 적어라.** "왜 이게 더 나은지" 빠지면 같은 실수 반복.
- 코드가 안 명확하면, 리뷰 코멘트에 설명을 적게 하지 말고 **코드를 다시 쓰게** 하라.

## 6. 저자(나)가 리뷰 코멘트에 응답하는 법

Opus 리뷰는 자동이지만, *수용할지 반박할지*는 의식적으로 결정해야 한다.

1. **감정 배제** - 리뷰 결과 본 직후엔 반박 금지. 한 호흡 두고 본다.
2. **수용이 기본** - 리뷰어가 옳을 확률이 더 높다고 가정.
3. **반박할 땐 근거로** - "이 코드는 X tradeoff 때문에 이렇게 갑니다. [이유]". 추측·취향으로 반박 금지.
4. **반복 충돌은 DECISIONS.md** - 같은 결정이 두 번째 부딪히면 `DECISIONS.md`에 기록해서 다음에 또 안 부딪히게.

## 8. 리뷰 출력 포맷

영역별 CODE_REVIEW와 동일 포맷. **`## 👍 Good` 섹션을 추가**해 잘한 부분도 명시 (멘토링/self-discipline 효과).

    ## 🚨 Critical
    - 파일:line - 문제 - 수정 방향

    ## ⚠️ Major
    - 파일:line - 문제

    ## 💡 Nit / 📌 FYI
    - 파일:line - 제안

    ## 👍 Good
    - 잘한 부분 1-3개

    ## ✅ 통과
    - 확인 항목 요약 (1-2줄)

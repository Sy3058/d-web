# 코드 리뷰 원칙

영역별 체크리스트(`CODE_REVIEW_BE.md` / `CODE_REVIEW_FE.md` / `CODE_REVIEW_ADMIN.md`)와 함께 사용한다.
체크리스트가 *무엇을 검사하는가*라면, 이 문서는 *어떻게 리뷰하고 응답하는가*를 정한다.

기반: [Google Engineering Practices - Code Review](https://google.github.io/eng-practices/review/) 를 1인 프로젝트 맥락에 맞게 각색.

---

## 0. 이 프로젝트의 맥락

- 저자 = 나
- 리뷰어 = `$fable-review` workflow를 적용한 현재 리뷰 에이전트. 메인 Astra가 작업 난도에 맞는 reasoning으로 직접 판단하며, 모델·위임 기준은 `docs/guides/GUIDE_WORKFLOW.md`를 따른다.
- 따라서 Google 원칙 중 *팀 협업 절차*(응답 SLA, 멘토링, 에스컬레이션)는 *self-discipline 강화*로 재해석한다.

---

## 1. 리뷰의 기준 (Standard)

**완벽이 아니라 "코드 헬스를 개선하는가"가 기준.**

- 머지 전 상태보다 명확히 개선되었다면 승인. "더 좋게 만들 여지가 있다"는 이유만으로 머지를 막지 않는다.
- 추가 개선은 후속 PR/이슈로 분리.
- 단, **🚨 Critical은 예외** - 보안·데이터 무결성 위반은 항상 머지 금지.

---

## 2. 후속 작업의 처리

- 요청의 완료조건에 필요한 수정은 같은 작업에서 해결한다. 무관한 개선은 구현 범위를 늘리지 않고 필요할 때만 보고한다.
- 남기는 TODO에는 구체적인 이유와 완료조건을 적고, 관련 이슈가 이미 있으면 연결한다. 이슈 등록 권한이 없으면 초안이나 로컬 기록으로 남기며 외부 게시를 자동으로 요구하지 않는다.

---

## 3. Small PR 원칙

(`guides/GUIDE_COMMIT.md`의 "한 커밋 하나의 변경"을 PR 단위로 확장)

- 한 PR = 하나의 자기완결적 변경
- 줄 수는 경고 신호일 뿐 기준이 아니다. 한 번에 검증 가능한 자기완결적 변경인지 판단한다.
- 리팩토링은 기능 변경과 분리된 PR
- 큰 작업은 독립 검증 가능한 단위로 나눈다. 스택 PR·브랜치 생성은 사용자 요청과 Git 규칙을 따른다.

---

## 4. 리뷰어가 확인할 일반 관점

영역별 체크리스트는 *이 프로젝트 특유의 violation*에 집중한다.
그 외 다음은 항상 검토:

| 항목 | 질문 |
|------|------|
| Design | 변경이 이 모듈에 속하는가? 추상화 위치가 맞는가? |
| Functionality | 의도대로 동작하는가? 엣지 케이스·동시성은? |
| Complexity | 빠르게 이해되는가? 미래에 필요할 법한 일반화는 없는가? |
| Tests | 변경에 맞는 테스트가 있는가? 테스트가 실제로 실패할 수 있는가? |
| Naming | 의미를 충분히 전달하고 과도하게 길지 않은가? |
| Comments | "왜"를 설명하는가? "무엇"을 설명한다면 코드를 단순화하라. |
| Consistency | 기존 코드 컨벤션을 따르는가? |
| Documentation | 빌드·환경·API 변경 시 관련 문서도 업데이트했는가? |
| Context | 이 변경이 시스템 전체 헬스를 올리는가, 복잡도만 늘리는가? |

## 5. 리뷰 코멘트 작성 규약

### 5.1 심각도 prefix

영역별 CODE_REVIEW의 4단계와 정렬:

| Prefix | 의미 | 머지 영향 |
|--------|------|-----------|
| `🚨 Critical` | 보안/데이터 무결성 위반 | **머지 금지** |
| `⚠️ Major` | 버그 가능성, 유지보수 악화 | 수정 필요 |
| `💡 Nit:` | 스타일·미세 개선 | 머지 가능 (선택 수정) |
| `📌 FYI:` | 참고 정보, 미래 고려 | 머지 가능 |

### 5.2 톤

- 코드를 비판하라, 사람을 비판하지 마라.
  - ❌ "왜 여기 스레드를 썼나요?"
  - ⭕ "이 동시성 모델은 성능 이득 없이 복잡도만 늘립니다. 싱글스레드가 명확합니다."
- **이유를 함께 적어라.** "왜 이게 더 나은지" 빠지면 같은 실수 반복.
- 코드가 안 명확하면, 리뷰 코멘트에 설명을 적게 하지 말고 **코드를 다시 쓰게** 하라.

---

## 6. 저자(나)가 리뷰 코멘트에 응답하는 법

리뷰 결과를 *수용할지 반박할지*는 근거를 바탕으로 의식적으로 결정해야 한다.

1. 지적을 실제 정의·호출 경로·재현 결과와 대조한다. 리뷰어 또는 작성자의 권위만으로 수용하지 않는다.
2. 타당한 지적은 반영하고, 오탐은 근거와 트레이드오프를 설명한다. 불확실하면 먼저 검증한다.
3. 후속 작업에도 영향을 주는 결정만 `DECISIONS.md`에 기록한다.

## 7. 영역별 체크리스트와의 관계

| 문서 | 역할 |
|------|------|
| `GUIDE_REVIEW.md` (이 문서) | 리뷰 *방법*·*응답*·*원칙* |
| `CODE_REVIEW_BE.md` | FastAPI/SQLModel/결제/JWT 도메인 violation |
| `CODE_REVIEW_FE.md` | Astro/React 섬/Signed URL 도메인 violation |
| `CODE_REVIEW_ADMIN.md` | Vite React SPA/2FA/관리자 권한 도메인 violation |

리뷰 요청 시 공통 원칙과 영역별 체크리스트를 함께 적용한다:

    $fable-review로 docs/reviews/GUIDE_REVIEW.md와 docs/reviews/CODE_REVIEW_BE.md를 참고해 리뷰해줘

## 8. 리뷰 출력 포맷

발견을 심각도 순으로 파일·위치, 발생 조건, 영향과 함께 보고한다. 빈 심각도 섹션, 의무 칭찬, 모든 체크리스트의 통과 나열은 생략한다. 발견이 없으면 없다고 명시하고 검증 범위와 남은 공백만 설명한다. 영역별 출력 예시는 필요할 때 참고하며 고정 양식으로 강제하지 않는다.

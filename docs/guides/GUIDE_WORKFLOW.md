# 워크플로우 가이드

브랜치/커밋/PR/블로그 등 특정 행동을 할 때 따라야 할 룰을 모은 문서.
루트 `AGENTS.md`에는 매 세션 필요한 핵심만 두고, 행동별 룰은 여기에 둔다.

## 모델과 작업 위임

2026-09-11 사용자 결정. 메인 모델은 Astra(`gpt-6-astra`)이며, 프로젝트 기본 reasoning은 `medium`이다. Astra는 계획·오케스트레이션과 독립적인 최종 reasoning을 맡고, 구현은 기본 Sol에 위임한다.

| 작업 | 담당과 reasoning |
| --- | --- |
| 계획·오케스트레이션·일반적인 최종 검토 | 메인 Astra Medium, 필요하면 High |
| 구현 | `gpt-5.6-sol` Low |
| 막힌 디버깅·원인 가설이 풀리지 않는 실패 | Sol Medium 또는 High |
| 어려운 DB·동시성·보안·아키텍처 판단 | 메인 Astra XHigh 이상, 실행 환경에서 지원하면 필요에 따라 Max 또는 Ultra |
| 단순 검색·파일 탐색·확정된 규칙의 반복 수정 | 저비용 subagent, 기본 `gpt-5.6-luna` Low |

- 난도와 실패 증거에 따라 필요한 수준으로 올린다. Astra를 일상 작업 때문에 Low로 낮추지 말고, 어려운 판단이 끝난 뒤 확정된 일반 작업은 Sol 또는 Luna에 위임한다. 분야 이름만으로 모든 작업을 최고 수준으로 올리지 않는다.
- 지원되는 전환 기능이 있으면 매번 사용자에게 승인을 요청하지 않고 적용한다. 현재 세션에 전환 기능이 없으면 실제 전환했다고 말하지 않는다. 더 높은 설정이 작업 진행에 필요할 때만 필요한 설정과 실행 환경의 제한을 알린다. `.codex/config.toml`의 기본값 변경을 실행 중 세션의 즉시 전환으로 간주하지 않는다.
- 위임은 메인이 유용한 작업을 병행할 수 있는 독립적이고 한정된 하위 작업으로 나눈다. 단일 짧은 조회처럼 위임 비용이 더 크면 직접 처리한다.
- subagent에는 대상 파일·검색 질문·수정 규칙·완료 조건과 필요한 맥락만 전달한다. 모델과 reasoning을 명시할 수 있는 도구에서는 직접 지정하고, 전체 대화 상속이 모델 override를 막으면 필요한 맥락만 전달한다.
- 반복 수정은 메인이 규칙을 확정한 뒤 맡기며, 같은 파일을 동시에 편집하지 않는다. 저비용 모델이 불확실성이나 실패를 보고하면 메인이 인계받아 판단한다.
- 아키텍처 선택, 보안·결제 불변조건, 상충하는 근거의 해석, 독립적인 최종 reasoning과 리뷰 최종 판정은 메인 Astra가 직접 맡는다. 구현 담당 subagent는 아키텍처나 보안 결정을 대신하지 않는다. Council의 관점별 보조 검토를 쓰더라도 최종 판단과 합성은 메인의 책임이다.
- 메인은 subagent의 결과와 실제 diff·검증 출력을 확인한다. 위임은 기존 변경 보존, 브랜치·커밋·push 승인 규칙을 바꾸지 않는다.

설정 키는 [공식 Codex 설정 문서](https://learn.chatgpt.com/docs/config-file/config-reference)를 따른다. 모델 선택은 실행 환경에서 제공되는 모델을 기준으로 하며, Luna를 사용할 수 없으면 사용 가능한 저비용 모델을 확인해 선택한다.

## 브랜치 작업 규칙

브랜치 관련 작업 전 반드시 아래 순서를 지킬 것:
1. **현재 브랜치 확인**: 새 브랜치 생성/체크아웃/커밋 전 항상 `git branch --show-current` 또는 `git status`로 현재 위치 확인
2. **사용자 의도 확인**: 사용자가 이미 브랜치를 만들어 뒀거나, 다른 브랜치에서 작업 중일 수 있음 - 임의로 `git checkout -b` 실행하지 말 것
3. **새 브랜치 생성·전환은 사용자 확인 후**: 이미 받은 브랜치 작업 승인은 같은 범위에서 재사용한다.
4. **새 브랜치는 최신 main에서 분기**: 현재 브랜치가 main이 아니라는 이유만으로 잔재로 간주하지 않는다. 기존 작업의 후속 요청과 현재 worktree에서 안전하게 처리할 수 있는 수정은 계속한다. 별도 브랜치가 필요한 독립 작업이면 읽기·조사를 마친 뒤 작업 위치만 확인한다. 사용자가 명시적으로 요청한 스택 PR은 예외다.
5. **PR 푸시 후 브랜치 유지**: 브랜치를 자동으로 바꾸거나 pull하지 않는다. main 복귀나 후속 작업 위치는 사용자에게 확인한다.

브랜치 명명 규칙은 `DECISIONS.md` "브랜치 전략 결정" 참조.

## 커밋 작업 규칙

커밋(및 태그/푸시) 실행 전 반드시 아래 순서를 지킬 것:
1. **변경사항 검토 요청 필수**: `git diff` / `git status`로 변경사항을 요약해 보여주고 사용자 확인을 받은 뒤 커밋
2. **커밋 메시지 사전 공유**: 메시지 초안을 먼저 텍스트로 보여주고 OK 받은 후 실행
3. **diff와 메시지 공유 후 명시적 커밋 승인이 필요**: 특정 문구를 요구하지 않는다. 같은 변경 범위와 메시지에 이미 받은 승인은 다시 묻지 않는다.
4. **태그/푸시는 별도 확인**: 커밋 승인을 받았어도 `git tag`, `git push`는 다시 한 번 확인받고 실행
5. **`Co-Authored-By: Claude`, `🤖 Generated with Claude Code` 등 AI 생성 문구 절대 금지**
6. **커밋 메시지 형식**: `[PREFIX] type: 제목` (PREFIX는 `[BE]`/`[FE]`/`[ADMIN]`/`[INFRA]`/`[COMMON]`)

커밋 메시지 상세 가이드는 `GUIDE_COMMIT.md` 참조.

## PR 작성 규칙

PR 생성·게시 같은 외부 변경은 사용자의 명시적 요청이 있을 때만 수행한다. 요청이 없으면 본문 초안까지만 준비한다.
1. **`gh pr create`는 명시적 요청이 있을 때만 실행** - 요청이 없으면 본문 파일 작성까지만
2. **본문은 해당 영역의 PR 템플릿에 맞춰 작성**: 기본은 `pr_body.md`이며, 기존 초안과 충돌하면 별도 임시 파일에 준비한다.
3. **기존 내용 처리**: 현재 PR 초안 수정 요청이면 해당 초안을 갱신한다. 다른 작업의 초안은 보존하고 별도 파일을 사용한다. 파일이 비어 있지 않다는 이유만으로 작업을 중단하지 않는다.
4. **체크박스**: 사용자 판단이 필요한 항목은 비워두고, 명백히 완료/해당 없음인 항목만 표시

## 태그 / 버전 규칙

태그(및 푸시)는 `커밋 작업 규칙` 4번대로 실행 전 별도 확인을 받는다.
1. **태그 단위**: 태그는 **마일스톤 완료**(해당 PR이 main 머지된 뒤) 또는 릴리스에만 건다. 그룹·세부작업(예: M1의 그룹 C)엔 걸지 않는다.
2. **형식**: annotated 태그(`git tag -a`)를 main의 (squash) 머지 커밋에 단다. 경량 태그 금지.
3. **이름**: 출시 전 마일스톤 = `v0.N.0` (M1=`v0.1.0`, M1.5=`v0.1.5`, M2=`v0.2.0` …), 정식 출시(M7) = `v1.0.0`. 이후 semver.
4. **푸시 분리**: 태그 push는 사용자 확인 후 `git push origin <태그>` (커밋 push와 별개).

## 블로그 작성 규칙

세션 작업 내용을 블로그 글로 정리할 때는 `blog.md`에 작성한다.
1. **파일이 비어있으면**: 새로 작성
2. **기존 내용이 있으면**: 뒤에 덧붙이기 (구분선 또는 새 섹션으로 분리)
3. **기존 내용에 모순/낡은 정보가 있으면**: 수정
4. **운영 방식**: 사용자가 블로그에 옮긴 뒤 파일을 비워두므로, 비어있다고 놀라지 말 것
5. **톤**: 사용자의 기존 블로그 톤(1인칭, 캐주얼, 결정 과정·시행착오 솔직히 기록) 유지

## 세션 종료 규칙

완료 시 실제로 바뀐 계약·결정·검증 결과에 필요한 기록만 갱신한다. 이미 기록한 내용은 반복 작성하지 않는다.
1. 이번 세션에서 실수하거나 막혔던 것 확인
2. 재발 방지 가치가 있는 교훈만 기존 항목과 대조해 기록한다. 일회성 실패마다 새 규칙을 추가하지 않는다:
   - 치명적 → 루트 `AGENTS.md`의 불변조건 또는 관련 가이드에 추가
   - 영역별 반복 → `backend/AGENTS.md`, `frontend/AGENTS.md`, `admin/AGENTS.md` 중 관련 파일에 추가
   - 가끔 참고 → `docs/MISTAKES.md`에 추가
3. `study/` 폴더 업데이트 여부 확인:
   - 사용자가 학습을 요청했거나 학습 대화에서 다룬 재사용 가치 있는 개념만 `study/concepts/`에 기록한다. 에이전트가 조사한 모든 기술을 새 학습 과제로 만들지 않는다.
   - `study/sessions/`는 학습 맥락 보존이 필요할 때 작성한다. 결정·구현 문서와 같은 내용을 중복 작성하지 않는다.
4. `docs/` 폴더 업데이트 여부 확인:
   - 기술 스택/기능 결정이 바뀌었거나 추가됐으면 → `docs/DECISIONS.md` 업데이트
   - DB 스키마 변경이 있었으면 → `docs/DB_SCHEMA.md` 업데이트
   - 마일스톤 작업을 완료했으면 → `docs/milestones/` 해당 문서 업데이트
   - **구현(코딩) 작업이었으면 → `docs/MODULES/{영역}/{모듈}/IMPLEMENTATION_*.md` 작성 여부 확인** (모듈 단위 구현·결정 기록, 양식은 기존 문서 참고. 사소한 수정은 생략 가능. 2026-07-09 명문화: 트리거가 없어 M1.5 A1~C1 내내 누락됐던 항목 - PR 템플릿 체크박스만으로는 안 잡힘)
5. 위 항목 모두 변경사항 없으면 생략
6. **타이밍/커밋**: 가능하면 PR push 전에 이 정리를 돌려 같은 PR에 포함한다. push 뒤 필요한 문서 변경을 발견하면 다른 작업 브랜치로 자동 이월하지 말고 현재 상태를 사용자에게 보고해 반영 위치를 확인한다.

# Task Harness 가이드 (작업 진행 프레임워크)

작업을 시작할 때 **무엇을·어떻게·어디까지** 할지 한 장으로 고정하고(= [A] GOAL 입력판), 그 위에서 **늘 같은 방식으로 진행**(= [B] 고정 루프)하기 위한 프레임워크.

사용자가 harness를 요청했거나 여러 세션에 걸친 작업의 상태 보존이 필요할 때 적용한다. 단순 수정·질문·리뷰에는 입력판이나 ledger를 강제하지 않는다. 사용자 요청과 이미 받은 권한이 양식보다 우선한다.

- 마일스톤 doc(M1, M2 …)이 "여러 goal의 지도"라면, 이 문서는 "goal 하나를 어떻게 정의하고 굴리는가"의 규칙이다.
- 브랜치/커밋/PR 규칙은 `docs/guides/GUIDE_WORKFLOW.md`, 리뷰 원칙은 `docs/reviews/GUIDE_REVIEW.md`와 병행한다.
- 계획·설계는 `$fable-plan`, 구현·디버깅은 `$fable-exec`, 리뷰는 `$fable-review`를 사용한다. 분해는 **검증 가능한 단일 goal까지만** 한다.

---

## 2층 구조

```
[A] 작업마다 입력판을 채운다  →  [B] 고정 루프가 그 위로 돈다
```

- 입력판은 요청과 저장소 근거에서 채운다. 누락된 형식 항목만으로 중단하지 않으며, 결과를 바꾸는 필수 선택이나 권한이 없을 때만 확인한다.
- **운영 방식**: 작업 착수 시 [A] 7칸을 채워 강 모델(오케스트레이터)에게 kickoff로 전달한다. 입력판은 **커밋하지 않는 작업 지침**이지만 **채팅에만 두지 않는다** - 채팅은 길어지면 요약·소실되고 "뭘 했고 안 했는지"를 체크할 수 없다. 대신 **gitignore되는 ledger 파일**(레포 루트 `*.local`, 예: `task_harness.local`)에 **현재 goal 하나의** [A] 입력판 + [B] 체크리스트(단계 done/not-done, DONE EVIDENCE 검증 결과)를 적고, 진행하며 그 파일을 갱신한다(B5 외부 progress file). 강 모델은 같은 미완료 goal을 재개할 때 이 ledger의 마지막 검증 지점부터 이어 간다.

## [A] GOAL 입력판 - 작업마다 채운다

| # | 칸 | 채울 내용 |
|---|----|----------|
| 1 | GOAL | 측정 가능한 단일 목표. 확장 금지. |
| 2 | DONE EVIDENCE | 완료 증거(테스트/빌드/before-after metric/문서/배포 등). 검증 불가한 건 완료조건으로 쓰지 않는다. |
| 3 | CONTEXT | 현재 상태·기존 구조·이전 결정·관련 파일/의존성·알려진 제약. |
| 4 | STARTING POINT | 먼저 볼 파일/로그/테스트/문서/실패출력/기존계획. 여기서 시작하고 근거가 부족하면 관련 호출·의존 경로로 탐색을 넓힌다. |
| 5 | SCOPE | Include(수정 가능 영역 + 필요 작업) / Exclude(범위 밖·무관 리팩터·신기능·기존 API·schema·production behavior 임의 변경). |
| 6 | CONSTRAINTS | 각 허용/금지: 새 dependency / network·API / commit·PR·push / migration·DB / 비용 / destructive. |
| 7 | BUDGET | 시간·토큰·호출·비용 상한(있으면 따름, 없으면 임의 생성 금지). |

> 선택 항목은 해당 없음으로 두고, 합리적 가정은 명시한다. 사용자가 정하지 않은 예산 상한은 만들지 않는다.

### 빈 템플릿 (복붙용)

```
GOAL          :
DONE EVIDENCE :
CONTEXT       :
STARTING POINT:
SCOPE         : Include -
                Exclude -
CONSTRAINTS   : dependency -  / network·API -  / commit·push -  / migration·DB -  / 비용 -  / destructive -
BUDGET        :
```

## [B] 고정 루프 - 한 번 깔고 매 작업 동일 적용

이 절은 **상수**다. 매 작업/매 문서에 복붙하지 않고 여기 한 곳만 둔다.

> **누가 [B]를 도는가**: 현재 작업의 주 실행자가 PLAN GATE, RISKS 점검, VERIFY, WORKING/PARTIAL/BROKEN 판정을 소유한다. 위임은 사용자 지시와 현재 세션 정책이 허용할 때만 사용하며, 위임자의 자기보고는 완료 증거로 인정하지 않는다.

### B1. 항상-ON 가드 (위반 금지)

- **정직성(최우선)**: 실패·불확실·미검증을 숨기지 않는다.
- **성공 위장 금지**: 테스트 삭제/비활성/약화, mock·skip·xfail·threshold 완화, benchmark 조건 변경, 실패로그 은폐, hardcode, screenshot crop, 요구사항 재해석, acceptance criteria 약화, production behavior 변경으로 회피 - 전부 금지.
- **SOURCING(해당 시)**: 리서치·분석·외부 수치·외부 사실을 쓰면 출처를 붙인다. 출처 없는 구체 수치·가짜 출처 금지.
- 확신 없는 판단은 **불확실로 표시**.

### B2. PRIORITY (충돌 시 우선순위)

`0 정직성 → 1 안정성 → 2 기존 동작 유지 → 3 검증 가능성 → 4 성능 → 5 코드 정리`

### B3. 실행 루프 (PLAN → DO → VERIFY → FINALIZE → OUTPUT)

- **PLAN GATE**: 요청과 근거에서 짧은 실행 방향을 정한다. 구현 요청에 필요한 schema·dependency·behavior 변경은 승인된 범위에서 진행한다. 계획만 요청받았거나 범위를 실질적으로 확장해야 할 때만 구현 전 확인한다.
- **DO**: 목표를 완결하는 일관된 변경으로 달성한다. 해당 변경에 실제로 관련된 실패 시나리오를 검토한다.
- **VERIFY**: 변경 diff와 해당 범위의 테스트·정적 검사·빌드를 확인한다. 모든 검증 종류를 일괄 실행하지 않는다. 브라우저 실기능 확인은 사용자가 수행한다. 필요한 검증을 못 하면 **NOT RUN + 사유**를 명시한다.
- **FINALIZE**: 목표 달성 후 추가 리팩터 금지. 임시코드·debug·실패실험·잡파일 정리. 보고 전 범위 + 검증 재확인.
- **OUTPUT**: 변경 파일 / 핵심 수정 / 완료 증거 / 실행한 검증 / 리스크·trade-off / 남은 known issue / 후속 작업. **최종 상태: WORKING / PARTIAL / BROKEN.**

### B4. 확인이 필요한 경우

- 결과를 실질적으로 바꾸는 필수 사용자 선택이 없거나 지시가 충돌한다.
- 요청 범위 밖 변경, 승인되지 않은 파괴적 작업·외부 변경 또는 추가 권한이 필요하다.
- 안전한 진단과 대안을 확인해도 credentials·외부 상태 등으로 더 진행할 수 없다.

필수 답변에 의존하는 작업만 보류하고 독립적인 조사·구현은 계속한다. 목표 분해, 원인 불확실성, 첫 실패는 중단 사유가 아니다. 반복 실패 시 근거를 비교해 가설·접근법·reasoning을 바꾸고, 진전 없는 동일 재시도는 피한다.

### B5. 장기 작업 (해당 시)

- 주요 단계마다 짧은 상태 보고(완료 증거와 미완료를 분리).
- 외부 기록(progress file/checklist/commit/draft PR)에 상태 저장.
- 재개 시 마지막 검증 지점부터. 처음부터 다시 금지.
- 명시된 예산 상한을 지킨다. 소진 위험이나 장시간 정체는 현황과 다음 접근을 알리되 임의의 80% 지점에서 승인을 다시 요구하지 않는다.

## 로컬 실행 모델 모드 (선택 사항)

**이 절은 사용자가 로컬 실행 모델 위임을 명시적으로 요청했고 해당 실행 수단이 제공된 경우에만 적용한다.** 일반 작업에는 적용하지 않으며, 현재 세션의 에이전트 지침과 위임 정책이 우선한다.

소형 모델은 다단계 지시·범위 판단·자기검증·근본원인 추론을 신뢰성 있게 못 한다. 그래서 9B에 위임할 땐 **판단은 강 모델이 다 끝내고, 소형 모델에는 "정해진 것을 타이핑"만 남긴다.** 9B를 보일러플레이트로 좁히는 이유는 토큰 경제다: **짧은 명세로 대량 출력이 나오고 검증이 기계적**인 일에서만 위임이 이득이고, 맞춤 로직·컴포넌트는 강 모델 직접 작성이 더 싸고 정확하다.

### 역할 분리

| 역할 | 누가 | 담당 |
|------|------|------|
| 오케스트레이터 / 플래너 / 검증자 | **강 모델** | 마일스톤 task를 micro-goal로 분해, [A] 입력판 작성, [B] 전체(PLAN GATE·RISKS·VERIFY·FINALIZE·판정·STOP) 수행, 실패 시 재분해 |
| executor | **소형 모델(9B)** | micro-goal **하나**의 B3 DO만 = 지정된 파일에 지정된 코드를 작성. 게이트·검증·범위판단·완료판정 안 함 |

> **executor에게 [B]를 통째로 주지 말 것.** 9B는 PLAN/VERIFY/판정을 "하는 척"하게 되고 이는 B1이 금지한 **성공 위장**이다. 9B의 출력은 강 모델이 검증하기 전까지 **미검증**으로 취급한다.

### 분해 원칙 (micro-goal 사이징)

아래 사이징은 **9B 경로(보일러플레이트 위임) 전용**이다. 강 모델 직접 작성 경로는 과분해하지 않고 검증 가능한 단일 goal에서 멈춘다. 9B에 위임할 땐 강 모델이 각 micro-goal을 **9B가 한 번에 실수 없이 끝낼 크기**로 쪼갠다.

- **1 micro-goal = 1 파일 · 1 관심사** (한 함수 / 한 스키마 / 한 컴포넌트). "회원가입 구현"이 아니라 "파일 F에 필드 X·Y의 Zod 스키마 작성".
- **판단 0**: 설계·네이밍·구조·라이브러리 선택은 강 모델이 미리 결정해 **CONTEXT/CONSTRAINTS에 박는다**. executor는 결정하지 않는다.
- **STARTING POINT는 정확히**: 정확한 파일 경로 + 앵커(함수 시그니처 / 삽입 위치) + **모방할 기존 예시 코드**. 9B에선 "광역 탐색 금지"가 필수다.
- **SCOPE.Exclude로 과잉편집 차단**: "이 파일 외 수정 금지 / 리포맷 금지 / 다른 함수·import 건드리기 금지". 소형 모델이 시키지 않은 곳을 고치는 사고를 막는다.
- **DONE EVIDENCE = 강 모델이 돌릴 결정적 명령** (특정 테스트 · 타입체크 · 빌드). executor 자기보고는 완료 증거가 아니다.

### 검증 플로우 (3 게이트 → 판정 → 실패처리)

분해(쪼개기)는 **실패율을 낮추는 것**이고, 이 절은 **남은 실패를 잡는 것**이다. 둘은 같이 간다.

**전제**
- **9B 출력은 검증 통과 전까지 미검증(untrusted).** "9B가 됐다고 함"은 증거가 아니다(B1 성공위장 금지).
- **싼 검증부터 쌓고 fail-fast.** 앞 게이트에서 깨지면 뒤 게이트(빌드 등)는 안 돌린다.

**3 게이트** (앞일수록 싸고 자주 잡힘)

| 게이트 | 무엇 | 어떻게 | 잡는 것 |
|--------|------|--------|---------|
| 1. 범위·계약 | 정적, 실행 없음 | `git diff --stat`(대상 1파일만 바뀜?) + diff 내용(WHERE 밖·금지영역 건드림?) + SPEC 대조(시그니처·export·import 일치?) | 과잉편집, 계약 드리프트 (예: 다른 스키마 수정, `export default`→named) |
| 2. 기계 검증 | 명령 실행 | 파일을 실위치에 놓고 DONE EVIDENCE 명령: 타입체크 / lint / 테스트 / 빌드 | 컴파일·타입·테스트 실패 (객관적) |
| 3. 의미·보안 | 주 실행자 판단 | 목표 달성·엣지케이스 + 프로젝트 보안 위반 점검(`docs/reviews/CODE_REVIEW_*.md`) | 로직 오류, 보안 위반 (localStorage JWT·Signed URL·클라 결제 등) |

- 게이트 1·2는 거의 자동화 가능, **3만 강 모델이 꼭 필요**하다. 게이트 1에서 깨지면 2·3 안 간다.
- 격리: 사용자 변경과 겹칠 수 있는 실파일을 자동 복원하지 않는다. 가능하면 scratch에서 게이트 1을 통과한 뒤 배치하고, 실패 산출물은 diff로 정확한 소유 범위를 확인해 `apply_patch`로 제거한다.

**판정**: WORKING / PARTIAL / BROKEN. 못 돌린 검증은 **NOT RUN + 사유** 명시.

**실패처리 = 재시도 ❌ 재분해 + 에스컬레이션** (같은 프롬프트로 다시 돌리지 말 것)

| 실패 클래스 | 대응 |
|---|---|
| 과잉편집(금지영역 수정) | DO NOT 강화 + WHERE 더 좁게 |
| 계약 드리프트(export/시그니처 틀림) | SPEC에 **정확한 시그니처·export 줄을 박음** |
| 로직 버그 | 어려운 하위 관심사를 **별도 micro-goal로 추출**(더 쪼갬) |
| 환각 API/import | 정확한 import 줄을 SPEC/PATTERN에 박음 |

- **하드 캡: micro-goal당 executor 시도 ≤2회.** 2회 실패 = STOP RULES("같은 blocker 반복") → 강 모델이 직접 작성.

**결정 규칙 (무한히 쪼개지 말 것)**

> 9B를 쓸 가치 = `(executor 프롬프트 + 검증 비용) < (강 모델 직접 작성 비용)`.

- 배럴 export·재export·단순 래퍼처럼 **기계적·결정적**인 파일 → 9B 이득.
- 상태·에러처리·로직 있는 컴포넌트처럼 **명세가 코드만큼 길고 검증이 깊은 읽기**를 요구하면 → 각 조각이 기계적이 될 때까지 쪼개거나, 안 쪼개지면 강 모델이 직접 작성.
- 두 종료조건 중 먼저 닿는 쪽에서 강 모델이 인수: **(a) executor 2회 실패**, 또는 **(b) "명세 길이 ≈ 코드 길이"가 되는 지점**.

### executor 프롬프트 템플릿 (9B에 실제로 건네는 것)

[A] 입력판은 강 모델의 **완전한 설계 명세**다. executor에는 그중 **판단이 제거된 명령 부분만** 트림해서 준다.

```
TASK   : <한 문장 명령. 예: 아래 파일에 함수 X를 추가하라>
FILE   : <정확한 경로 하나>
WHERE  : <삽입 위치 앵커 - 시그니처 / 줄 / 기존 함수 바로 아래 등>
SPEC   : <입출력·시그니처·동작. 강 모델이 이미 다 정해둔 것>
PATTERN: <모방할 기존 코드 예시 (같은 repo에서)>
DO NOT : 이 파일 외 수정 금지 / 리포맷 금지 / 다른 함수·import 변경 금지 / 새 의존성 금지
OUTPUT : 수정된 파일 내용(또는 해당 부분)만. 설명·잡담 없이.
```

> executor 프롬프트엔 PLAN/VERIFY/판정/STOP을 넣지 않는다(그건 강 모델 몫). executor가 "완료" "테스트 통과"라고 적어도 **그건 증거가 아니다** - 강 모델이 DONE EVIDENCE 명령으로 확인한다.

## 기존 마일스톤 양식과의 매핑

현재 `docs/milestones/*.md`의 task 블록(선행/산출물/DoD/결정/메모)은 이미 입력판 내용을 다른 이름으로 담고 있다. 리네이밍 + 4칸 보강이면 된다.

| 마일스톤 task 필드 | → 입력판 칸 |
|---|---|
| 선행 | CONTEXT (의존성) |
| 산출물 | GOAL + SCOPE.Include |
| DoD | DONE EVIDENCE |
| 결정 | CONSTRAINTS + CONTEXT |
| 메모 | CONTEXT / 알려진 제약 |
| (신규) | STARTING POINT |
| (신규) | SCOPE.Exclude |
| (신규) | CONSTRAINTS 허용/금지 체크리스트 |
| (신규) | BUDGET |

## 운영 규칙

- **마일스톤 doc = 지도, 입력판 = 단일 goal.** 마일스톤 전체를 입력판 한 장에 넣지 않는다. 한 task에 착수할 때 그 task를 입력판으로 펼친다.
- **입력판은 ledger 파일로 유지한다(채팅 전용 금지).** [A] 7칸 + [B] 체크리스트(단계 done/not-done, DONE EVIDENCE 검증 결과)를 gitignore되는 `*.local` 파일(예: 레포 루트 `task_harness.local`)에 적고 진행하며 갱신한다. 이유: 채팅은 컨텍스트 요약으로 잊히고 "정확히 뭘 했고 안 했는지"가 검증 불가하다. 재개 시 이 파일의 마지막 검증 지점부터 잇는다(B5).
- **ledger 하나에는 현재 goal 하나만 둔다.** 같은 미완료 goal을 재개할 때만 기존 내용을 이어 쓴다. DONE EVIDENCE를 충족하고 결과를 문서·커밋·PR 등 지속되는 기록에 남긴 goal은 다음 goal 착수 전에 ledger에서 제거하고 새 입력판으로 교체한다. 완료된 goal을 누적 append해 이력 파일로 만들지 않는다. `PARTIAL`·`BROKEN` goal은 사용자가 중단을 확정하거나 후속 기록 위치를 정하기 전까지 보존한다.
- **끝난 작업 소급 재작성 금지.** 이미 완료(✅)된 task를 새 양식으로 다시 쓰지 않는다. **다음 작업부터** 적용.
- **[B]는 이 문서에만 1회.** 작업마다 복붙하지 않는다.
- **소형 로컬 모델로 실행할 땐 "로컬 실행 모델 모드"를 따른다** - 강 모델이 분해·검증을 소유하고, 9B에는 판단 제거된 DO만 트림해 건넨다.
- 보안·결제 등 민감 작업은 메인 Astra가 난도에 맞는 reasoning으로 판단하고, 모델·위임 기준은 `docs/guides/GUIDE_WORKFLOW.md`를 따른다. `$fable-review`와 `docs/reviews/GUIDE_REVIEW.md`를 적용한다.

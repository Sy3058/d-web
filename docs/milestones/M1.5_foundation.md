## 의존성 다이어그램

```
[A] 작품 도메인 모델 + 마이그레이션 (works · tags · works_tags · episodes)
      ↓
[B] 관리자 인증 (role RBAC 가드 + TOTP 2FA 2단계 로그인 + 부트스트랩)
      ├──────────────┐
      ↓              ↓
[C] 작품 CRUD API   [D] R2 + 에피소드 업로드 (변환 · image_keys 순서 · 임시저장)
      └──────────────┘
                    ↓
            [E] 에피소드 공개 예약 스케줄러
                    ↓
            [F] 관리자 SPA 프론트 (로그인+TOTP · 작품 · 업로드 · 예약)
                    ↓
            [G] M1.5 완료 검증 (e2e DoD)
```

- A는 모든 도메인 작업의 선행. B(관리자 인증)는 A와 병렬 착수 가능(users 테이블만 의존).
- C/D는 B(`require_owner` 가드) 확정 후 병렬. D는 C의 work_id가 있어야 에피소드를 매달 수 있으나, 모델(A)만 있으면 계약은 맞출 수 있음.
- E는 episodes(A) + 업로드(D) 후. F(프론트)는 C/D/E **API 계약 확정 후** 시작(백엔드 미완성분은 mock 선행 가능).

> **외부 블로커**: **M0 인프라 - Cloudflare R2 버킷 생성 + 액세스 키 + 커스텀 도메인**(README M0 미완). 그룹 D 진입 전제. 미완료면 D 진입 불가(A~C·B는 R2 없이 진행 가능).

## 설계 결정 (2026-06-28 확정, 2026-06-29 RBAC 추가, 2026-07-01 3-역할 확정)

PRD/README가 모순·미결로 남긴 지점을 착수 전 확정. 상세 근거는 채팅 합의 기록.

### 결정 1: 업로드/변환 = 백엔드 경유 변환 (presigned PUT 미사용)
- 흐름: **클라이언트가 원본 이미지를 백엔드로 multipart POST → 백엔드가 Pillow로 가로 800px WebP 변환 → 백엔드가 R2에 업로드** → `episodes.image_keys`에 R2 키를 순서대로 저장.
- 이유: presigned PUT 직업로드는 클라가 R2로 직접 올려 **서버가 바이트를 못 봐 변환 불가**(ADM-03 "서버 변환"과 모순). 백엔드 경유는 (a) 변환·규격을 서버가 보장(미결제 유료 콘텐츠 보호 맥락 정합), (b) R2 자격증명/키를 클라에 미노출, (c) 단일 흐름이라 단순. 대역폭 이중(클라→VPS→R2)은 R2 egress 무료 + 1인 작가 저빈도 업로드라 비용 무의미.
- 탈락: B(presigned 직업로드+사후 변환)는 서버가 결국 CPU를 쓰는데 왕복·고아키 정리만 복잡. C(클라 변환)는 신뢰 불가(규격 우회) + "서버 처리"(Q11) 위반.

### 결정 2: WebP 변환 타이밍 = 1차 동기(요청 내), 초과 시 워커 분리 (Q23)
- 변환은 업로드 요청 안에서 **`anyio.to_thread.run_sync`로 오프로드**(M1 bcrypt와 동일 패턴 - 이벤트 루프 비블로킹). 50장 ≈ 수 초~10초 응답을 진행바로 커버.
- **새 인프라 0**(Redis/워커 없음). README 가이드("1차 동기, 응답 1초 초과 시 워커 분리") 정합 + YAGNI. 배포 후 변환 응답이 일관되게 길면 **그때** Arq+Redis로 분리(escalation 트리거: 50장 변환 wall-clock이 사용자 체감 한계를 넘거나 동시 업로드 발생).
- ⚠️ 관련 함정(MISTAKES): 동기 CPU 작업을 `async def`에서 직접 호출 금지 → 반드시 to_thread. Pillow는 GIL 영향받는 CPU 바운드라 to_thread는 "루프 비블로킹"이지 "병렬 가속"이 아님(그 요청 응답은 여전히 합산 시간 대기).

### 결정 3: TOTP 시크릿 저장 = Fernet 암호화 at-rest
- `users.totp_secret`는 **Fernet 대칭 암호화**해서 저장. 키 `TOTP_ENCRYPTION_KEY`는 env(`SecretStr`), **`jwt_secret`·`password_pepper`·`token_pepper`와 별도 키**. 검증 시 복호화 후 코드 대조.
- 이유: TOTP는 검증 때마다 원본이 필요해 단방향 해시(bcrypt) 불가 → 암호화 vs 평문 선택. (a) 이 프로젝트는 비번/refresh/이메일 토큰을 전부 "DB 단독 유출" 위협으로 보호(pepper-전부) → 가장 민감한 관리자 TOTP 평문은 자세 불일치. (b) **일일 R2 DB 덤프 백업이 실제 "DB만 유출" 경로** → 암호화 시 덤프엔 쓸 수 없는 암호문만. 단일 VPS 전체 탈취(env 동반 유출)엔 무력하나 부분 유출엔 실효.
- 시크릿 1개라 키 로테이션 비용 trivial. 분실 복구는 운영자가 env 키로 복호화 가능(DECISIONS "분실 시 DB 직접 조작"과 양립). 백업 코드는 1차 제외(DECISIONS).

### 결정 4: 관리자 권한 분리 = 3-역할 RBAC (reader/owner/moderator), M1.5 owner 단독 빌드 (2026-07-01)
- 운영자(작가)와 커뮤니티 운영자가 다른 사람일 수 있다. `users.is_admin`(boolean) → `users.role`(**VARCHAR(16)**, default `reader`)로 교체. 값: `reader`(일반)·`owner`(콘텐츠·매출·정산·환불+모더레이션)·`moderator`(게시글 삭제·문의 답변만) 셋.
- **모델은 3-역할로 열고, M1.5에서 실제 빌드·프로비저닝은 `owner` 하나뿐.** moderator=M4(owner가 런타임 부여). 각 역할은 그 역할의 in-product 엔드포인트가 생길 때 도입(빈 껍데기 계정 안 만듦). VARCHAR이라 후속 역할 추가는 Python enum 값+가드만, **DB 마이그레이션 0**.
- **authz 진실 소스 = DB `user.role`**(JWT claim 아님): `get_current_user`가 이미 매 요청 `User`를 DB 로드 → `user.role` 읽기는 추가 쿼리 0 + 항상 최신(강등 즉시 반영). JWT는 `sub`만 유지(M1 minimal-JWT). `/auth/me`가 `role` 노출(FE 가드용, 인가 아님).
- 가드: `require_role(*roles)` 팩토리. **M1.5는 `require_owner`만 사용**. 모더레이션은 M4 `require_role(OWNER, MODERATOR)`(owner ⊇ moderator). 일반 열람·구매는 role 아닌 "인증됨"으로 게이팅(moderator도 정상 유저).
- **개발자는 product 역할이 아니다 (developer 미도입)**: 개발자 ≠ 운영자는 실재하나, 개발자 일(에러=Sentry, 가동=UptimeRobot, 리소스=Hetzner)은 외부 도구 + 인프라 계층이라 product 계정·엔드포인트가 없다. 자체 관측 대시보드는 전문 도구 재발명이라 미채택 → `developer`를 역할로 만들지 않음. 개발자 매출 차단은 라우트 가드가 아니라 인프라/자격증명 소유권(진짜 장벽 M7). 필요해지면 그때 값 추가(VARCHAR라 DB 변경 없음).
- 2FA: owner 필수(M1.5). moderator 2FA는 M4 결정. 부트스트랩 `scripts/promote_admin.py`로 owner 승격(공개 가입 없음).
- ⚠️ **매출 차단 = soft control**: 개발자가 인프라(VPS·DB)를 통제하면 라우트 가드는 *앱 경로*만 막고 DB 직접 `SELECT`는 못 막는다. 실무에선 이 벽을 자격증명/도구 소유권(owner가 DB·결제도구 로그인 쥠)으로 친다. 진짜 정보 장벽은 작가가 DB 자격증명을 쥐는 **M7 인프라 분리** 시에만. 상세 DECISIONS "관리자 권한 분리".
- **정산은 단수**: role은 N계정 허용(owner 여럿 가능)이나 정산/지급 대상은 owner 수에서 파생 안 함 - 단수 작가 정체성에 묶음(M5).

  - `works.deleted_at` soft delete(하드 삭제 금지). `status` ∈ ongoing/completed/hiatus.
- 메모: `down_revision`은 **마이그레이션 생성 시 실제 head를 확인**(M1 A 절대수명 cap 마이그레이션이 현재 head). autogenerate 후 파일 Read로 확인, 손편집 금지(MISTAKES Alembic).

## 그룹 B. 관리자 인증 (role RBAC 가드 + TOTP 2FA)

> ⚠️ 보안 그룹. 계획·코드 모두 Opus 검증 생략 금지. M1 패턴 재사용: `oauth_tx`형 단명 서명쿠키(2FA pending 운반), `set_auth_cookies`/`clear_auth_cookies`(+`login_hint`), `require_verified_email`형 의존성, rate limit.
>
> **"일반 유저 DB와 분리"(ADM-01) 해석**: 별도 테이블 아님. 같은 `users` + `role`(VARCHAR, reader/owner/moderator). 분리의 실체는 **role 기반 가드(M1.5는 `require_owner`) + 별도 로그인 플로우 + 2FA 게이트 + 관리자 SPA(admin.도메인)**. M1.5는 owner만 빌드(moderator=M4).

### B1. users role enum + TOTP 컬럼 마이그레이션 + Fernet 설정 + 부트스트랩 ✅

> ✅ **완료**(브랜치 `be/feat/admin-auth-totp`): `RoleEnum`(VARCHAR(16)) + `is_admin`→`role=owner` 데이터 이관 마이그레이션(`9a25c6be3759`), `totp_secret`/`totp_confirmed_at` 컬럼, `lib/totp.py`(Fernet 암복호 + pyotp 래퍼), `config.py`+CI+`.env.example`의 `TOTP_ENCRYPTION_KEY`, `scripts/promote_admin.py`(owner 승격), 단위 테스트(TOTP round-trip·role 기본값·부트스트랩 플로우). `alembic check` 클린 + 데이터 이관 실측 확인. **`require_owner` 가드·TOTP 발급/검증·2단계 로그인은 B2/B3(후속 PR).**

- 선행: A 불요(users 기존)
- 산출물: `models/user.py`에 `role`(VARCHAR(16), default `reader`; Python `RoleEnum` 값 검증) + `totp_secret`(암호문, nullable) + `totp_confirmed_at`(nullable) 추가 + **`is_admin` 컬럼 제거**, 마이그레이션 1개(기존 `users` ALTER: `is_admin=true`→`role=owner` 데이터 이관 후 drop). `config.py` `TOTP_ENCRYPTION_KEY`(`SecretStr`, default 금지) + `.env.example`. `lib/totp.py`(Fernet 암복호 + pyotp 래퍼). 관리자 부트스트랩 스크립트 `scripts/promote_admin.py`(owner 승격, `uv run`).
- DoD: 마이그레이션 upgrade/`alembic check` 클린, 기존 `is_admin=true`행 → `role=owner` 데이터 이관 확인. Fernet 암→복 round-trip 테스트. 부트스트랩 스크립트로 기존 이메일인증 유저를 `role=owner`로 승격 확인.
- 결정:
  - **역할 모델**: `role` VARCHAR(16) `reader`(기본)/`owner`/`moderator`(Python enum 검증, 네이티브 PG enum 아님 → 후속 역할은 앱 코드만·DB 마이그레이션 0). **M1.5는 `owner`만 프로비저닝**(moderator=M4). authz는 DB `user.role`(JWT 미포함 - `get_current_user`가 이미 User 로드). `is_admin`은 폐기(마이그레이션 true→owner). 상세 결정 4 / DECISIONS "관리자 권한 분리".
  - 컬럼 의미: `totp_secret IS NULL` = 미등록. 등록 시 암호문 저장 + `totp_confirmed_at=NULL`(미확인). 첫 코드 검증 성공 시 `totp_confirmed_at` 세팅 = 활성. 로그인은 `totp_confirmed_at IS NOT NULL` 요구.
  - **부트스트랩(최초 관리자)**: 셀프 가입 경로 없음(공개 관리자 가입 = 보안 위험). 운영자가 스크립트로 기존 유저를 승격 → 그 유저가 B3 로그인 1단계(이메일/비번) 통과 후 **2FA 등록(B2)을 강제**받음. 승격은 destructive하지 않으나 외부 동작이라 실행 전 확인.
  - 새 의존성: `pyotp`(TOTP), `cryptography`(Fernet). 설치 직전 WebSearch 최신 안정 버전 확인.

## 메모

- **순서**: 계획(Opus) → 코딩(Sonnet) → 검증(Opus, `@docs/reviews/GUIDE_REVIEW.md` + `CODE_REVIEW_BE.md`/`CODE_REVIEW_ADMIN.md`) → 커밋. **2FA·TOTP·관리자 인증·업로드는 보안 로직이라 Opus 검증 생략 금지**(B·D는 Opus xhigh).
- 백엔드 실행은 항상 `uv run` 접두사. cwd 명시(`cd .../backend && uv run ...`, MISTAKES).
- 새 패키지(`pyotp`, `cryptography`, `Pillow`, `boto3`, `APScheduler`)는 설치 직전 WebSearch로 최신 안정 버전 확인(GUIDE_WORKFLOW 검색 규칙).
- **확정된 결정**(M1.5 착수 시 DECISIONS.md "보안/결제 결정"에 기록):
  - 업로드 = 백엔드 경유 변환(presigned PUT 미사용), 변환 = 1차 동기(`anyio.to_thread`)·초과 시 Arq
  - TOTP 시크릿 = Fernet 암호화 at-rest(`TOTP_ENCRYPTION_KEY`, pepper·jwt_secret과 별도 키)
  - 관리자 인증 = 같은 `users`+`role`(VARCHAR, reader/owner/moderator, RBAC; M1.5는 owner만), 2단계 로그인(이메일/비번 → TOTP), pending은 단명 서명쿠키, M1 인증 쿠키 인프라 재사용
  - 공개 예약 = APScheduler in-process 폴링 잡 + 원자 UPDATE(멱등)
  - "무료 회차 수" = `episodes.is_free` 단일 진실(별도 컬럼 없음)
  - 권한 분리(RBAC) = 3-역할(reader/owner/moderator), authz=DB `user.role`(JWT 미포함), `require_role`/`require_owner`. **M1.5는 owner만 빌드**(moderator=M4 owner 부여). 개발자는 product 역할 아님(외부 도구). **개발자 매출 차단**은 라우트 가드 아닌 인프라/자격증명 소유권(진짜 장벽 M7 - DECISIONS)
- 커밋은 영역 prefix `[BE]`/`[ADMIN]`/`[INFRA]`, 한 커밋 하나의 논리 변경(모델 → service → router → test → 프론트 분리, GUIDE_COMMIT).
- 진행은 ledger 파일(`task_harness.local`)에 [A] 입력판 + 단계 체크리스트로 추적(GUIDE_TASK_HARNESS). 그룹 착수 시 생성.
